# Shared castle world

Run `npm run play` from the project root, then open `http://127.0.0.1:5173`. The launcher starts the world server and the latest shared checkout's Vite preview, or reuses servers belonging to that checkout. It refuses to reuse an unrelated process on either port. Use the machine's LAN address and the same port on another device; TCP ports 5173 and 2567 must be reachable. For an HTTPS or separately hosted client, set `VITE_COLYSEUS_URL` to the HTTPS origin of a reachable Colyseus server when building the client.

Play opens a class picker, then connects the selected hero to the shared world. The server owns movement, patrols, health, attacks, projectiles, kills, the gate and core. An empty world continues simulating patrols. If everyone leaves an unfinished fight, the encounter resets. A victory records each participant's class and kills, displays a shared results screen with the round leaderboard and a 15-second server countdown, then starts a fresh round. A shared 20-minute day continues even while the world is empty; its clock and lighting are synchronized for everyone. A network drop reserves the player's seat for 20 seconds; the client tries to reconnect automatically. The pause menu stops local input; the shared world continues.

World checkpoints and result records live under `out/multiplayer/` by default; set `CASTLE_DATA_DIR` to select a persistent directory. The checkpoint is saved every two seconds and on departure. Idle patrol positions and round/time-of-day survive server restarts; an interrupted fight is reset because its players are gone. Results are append-only JSON lines, identified by a stable, hashed player identity. If a player leaves and their team subsequently wins, the later winning record supersedes their earlier departure record. These files are local development storage; production must mount durable storage and arrange backups. A single server process and room are supported; it accepts up to 24 concurrent players and rejects further joins instead of silently splitting the world.

`npm run typecheck:world` checks the server and `npm run test:multiplayer` runs an isolated server, browser client and automated second player through reconnection, victory, result storage and reset. `?scene=solo` retains the earlier local encounter as a test scene.

The deployed multiplayer server stores world checkpoints and results on a persistent volume; the filesystem result log is not a production database. Anonymous identity is stored in the browser and is lost if site storage is cleared. Player names are editable on the class selection screen and stored on the server under the authenticated identity. Joining again with the same identity replaces its previous session. A verified Wavedash identity starts with the host display name when available, otherwise a generated name; an in-game rename is kept in the server profile and takes precedence. Older profiles without a source marker switch to the Wavedash name only when their saved name matches that identity’s generated default. Wavedash identities use signed gameplay tokens; set `WAVEDASH_GAME_CLOUD_ID` on the server to accept them. Anonymous and Wavedash identities are separate and are not linked automatically. Public hosting needs an always-on WebSocket service, durable storage, TLS and appropriate access controls and monitoring. Static hosting alone cannot run the shared world. See the Wavedash and Railway deployment guide for the prepared release configuration and remaining checks.

## Network motion

The server is authoritative. Player input carries increasing sequence numbers; the local client predicts movement and replays inputs not yet acknowledged by the server. Other players, patrols and projectiles interpolate between received positions, with teleports snapping into place. Replicated player and projectile coordinates use 2.5 cm steps and enemy coordinates use 5 cm steps, avoiding updates for changes smaller than those grids. Checkpoint writes are asynchronous. Position fields are still encoded as floats; this quantization reduces change frequency rather than reducing each field’s encoded size.

Run `node game/tests/multiplayer-latency.mjs` for a local browser test with 250 ms of simulated server-to-client latency. It checks early predicted motion, convergence and patrol interpolation. This does not replace a playtest over a real remote connection or a device performance profile.

## AI teammates

The authoritative server fills a world target of ten total characters with AI teammates, choosing underrepresented Knight, Scout and Spellcaster classes. With an empty world, ten named AI teammates remain present. A small assault group advances on the gate and heart tree while others support them; all can occasionally chat using authored lines selected for the situation. Their fantasy names appear in the roster and chat; the development world monitor identifies them separately. Reserved, temporarily disconnected human seats count toward the party; teammates yield positions as humans join and resume helping when people return. Some accompany nearby humans, while the assault group advances independently. Across the party, bots can defeat at most two enemies per round and cannot reduce the heart tree below two health; humans can finish both. They use the same movement and combat simulation as human players, and are excluded from persistent human result records and session checkpoints. Their navigation and decision rules are an early prototype and need real playtesting.

For teammate chat, set `TYPESAFE_API_KEY` in the **server** environment to enable Jev selection from eligible authored lines. Local `npm run play` and `npm run dev:world` load `.env.local` when present; restart an already-running world server to pick up changes. Railway needs its own server environment variable and a deployment containing the chat code. Without the key, or if the API fails or times out, the server chooses a suitable local line. A response is dropped if the bot or game situation has changed. Only game-state facts and candidate lines are sent to TypeSafe, not player chat. Jev requests are made at most once per 45 seconds per world after an initial delay, and can incur API usage costs. The Jev choice has not yet been evaluated against reviewed playtest scenarios.

For an optional Jev comparison, set `CASTLE_JEV_SHADOW=1` and `TYPESAFE_API_KEY` in the server environment. This sends a compact anonymous world snapshot at most once every 30 seconds while humans and teammates are present. Server logs tagged `[teammate-advisor]` contain the input, baseline, Jev choice, confidence, model, token usage and latency; the decision is observational and never affects play. Requests have a three-second timeout and the game continues on failure. This consumes TypeSafe API usage when enabled. Evaluate recorded choices against independently reviewed cases and gameplay before considering control by Jev.

### Adding a test teammate

In the development preview, join the world and open **Debug (B)** → **Multiplayer** → **Add AI player**. Each click adds one server-controlled teammate, up to 24 total world actors. The button requires a server started with `CASTLE_DEV_DEBUG=1`; `npm run play` and `npm run dev:world` enable it for servers they start and configure test-tagged analytics against the selected development Convex deployment when its ingest credential is available. If a server was already running without that setting, restart the local world server for the button to become available. A manually added teammate stays while humans are connected, subject to room capacity. The setting must remain disabled on public servers.
